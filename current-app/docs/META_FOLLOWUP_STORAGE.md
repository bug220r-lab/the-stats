# Meta follow-up storage

The follow-up builder preserves all assets from the active Meta collection and creates a new immutable version. It does not alter the writable observation database, archives, earlier analyses, registry, or statistical results.

`scripts/preflight_meta_followup.py` records read-only hashes and SQLite checks of every registered database before collection. `stats_app/meta_followup.py` requires that preflight and refuses packaging if a database or registry hash changed. Its parent must be the active analysis recorded by preflight.

New source files are retained under `raw/meta_followup/`; normalized and mapping CSVs are exposed under `social/meta_followup/`. Previous `social/meta_collection/` tables remain byte-identical. Only the predecessor's package-level `metadata.json`, `raw_sha256.json`, and `audit/final_validation.json` are relocated to `raw/meta_followup_predecessor_metadata/`; their bytes remain unchanged, and all other assets keep their paths.

The required `normalized/collection_status.csv` uses `dataset,status,detail,evidence_ref,captured_at_utc`. Expected collection tables are `story_song_map.csv`, `story_metrics.csv`, `link_destinations.csv`, and `ads_coverage.csv`; additional native export tables may be supplied. No table is required to fabricate a row when evidence is unavailable. Status, source identity, exact capture time, reporting windows and raw source references belong in the collector's supplied schema. CSV `value`/`value_status` pairs are checked: unavailable values remain blank, observed values must be finite numeric evidence. A supplied capture timestamp must include an offset. Historical statistical input lineage remains pinned.

Build, stage and audit are separate operations. `build_meta_followup(parent, collection_root, output_dir, zip_path)` returns the package paths, label and `staging_metadata` for `stage_analysis_package`. Output package and ZIP paths must be new and outside the frozen collection input. It creates a raw file hash manifest and verifies every inherited asset against its original bytes. Existing output paths, overlapping directories and a predecessor that already contains this follow-up namespace are refused.

`scripts/audit_meta_followup_storage.py` independently checks the staged database against the predecessor, frozen collection files, and original ZIP. This is explicitly a **storage integrity audit**, not a semantic acceptance audit. Before activation, an independent review must additionally compare song assignments, audio evidence, destination URLs, Ads coverage and unavailable statuses against the actual source captures. The promotion audit must include those findings; a storage-only PASS is not evidence that a song or marketing claim is correct.

The Meta collection dashboard adds a separate Follow-up evidence view automatically. Earlier collection views remain available. A visible song reference or destination does not prove audio use, clicks, paid delivery, Spotify conversion or a causal effect. Empty Ads reports apply only to the observed account, dates and reporting scope. Original October 20 baseline membership remains unverified. TikTok collection is excluded.
